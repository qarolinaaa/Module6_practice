# ПРАКТИЧЕСКАЯ РАБОТА
## CSE5032 — Разработка веб-сервисов
### Модуль 06. Защита доступа к API

## 1. Цель работы

Целью практической работы является изучение способов защиты методов ASP.NET Core Web API с использованием API Key и JWT-аутентификации, а также освоение передачи данных авторизации через HTTP-заголовки.

## 2. Используемые технологии

В ходе выполнения работы использовались следующие технологии:

- C#;
- ASP.NET Core Web API;
- .NET 9;
- JWT Bearer Authentication;
- Swagger / OpenAPI;
- HMAC-SHA256.

## 3. Ход выполнения работы

### 3.1. Создание Web API

Был создан проект ASP.NET Core Web API на платформе .NET 9. Для работы с товарами разработана модель `Product`, содержащая следующие свойства:

- `Id` — уникальный идентификатор товара;
- `Name` — название товара;
- `Price` — цена товара.

В контроллере `ProductController` реализован метод `GET /api/product`, который возвращает список тестовых товаров. Для проверки работы API используется Swagger.

### 3.2. Защита API с помощью API Key

Для ограничения доступа к списку товаров реализована проверка API-ключа. Клиент должен передавать ключ в HTTP-заголовке `X-Api-Key`.

В качестве тестового значения используется `SecretKey123`.

Проверка ключа реализована в отдельном middleware `ApiKeyMiddleware`. Если ключ отсутствует или указан неправильно, сервер возвращает HTTP-статус `401 Unauthorized`. При корректном ключе запрос обрабатывается успешно и возвращает `200 OK`.

### 3.3. Настройка JWT-аутентификации

В проект добавлен пакет `Microsoft.AspNetCore.Authentication.JwtBearer`. В файле `Program.cs` настроена JWT-аутентификация.

Для проверки токена используются следующие параметры:

- Issuer — издатель токена;
- Audience — получатель токена;
- IssuerSigningKey — ключ проверки подписи;
- ValidateLifetime — проверка срока действия;
- ClockSkew — допустимое отклонение времени, установленное в ноль.

Также настроены middleware аутентификации и авторизации, обеспечивающие проверку токена перед предоставлением доступа к защищённым ресурсам.

### 3.4. Создание JWT-токена

В контроллере `AuthController` реализован метод `POST /api/auth/login`.

Для тестирования используются следующие учётные данные:

- Логин: `student`;
- Пароль: `12345`.

При успешной проверке учётных данных сервер формирует JWT-токен и возвращает его клиенту. Токен содержит информацию об имени и роли пользователя, уникальный идентификатор, издателя, аудиторию и время истечения срока действия.

Для формирования подписи используется алгоритм HMAC-SHA256.

### 3.5. Защита конечной точки

Для защиты метода получения товаров используется атрибут `[Authorize]`.

Защищённая конечная точка `GET /api/product/secure` требует одновременно правильный API Key и действительный JWT-токен.

Токен передаётся в HTTP-заголовке `Authorization` с префиксом `Bearer`. После успешной проверки сервер предоставляет доступ к ресурсу и возвращает сведения о пользователе, его claims и список товаров.

При отсутствии токена либо при неуспешной проверке сервер возвращает `401 Unauthorized`.

## 4. Проверка безопасности API

В ходе тестирования рассматриваются следующие сценарии:

| № | Сценарий проверки | Ожидаемый HTTP-статус |
|---|---|---|
| 1 | Запрос к списку товаров без API Key | `401 Unauthorized` |
| 2 | Запрос к списку товаров с правильным API Key | `200 OK` |
| 3 | Обращение к защищённому методу без JWT | `401 Unauthorized` |
| 4 | Обращение к защищённому методу с действительным JWT и API Key | `200 OK` |
| 5 | Обращение с изменённым JWT | `401 Unauthorized` |
| 6 | Обращение с просроченным JWT | `401 Unauthorized` |

Для проверки просроченного токена срок его действия временно устанавливается равным одной минуте. После получения нового токена и истечения срока действия выполняется повторный запрос к защищённой конечной точке.

Ожидаемые результаты позволяют проверить работу механизмов аутентификации и авторизации.

## 5. Результаты работы

В результате выполнения практической работы реализованы:

- Web API для получения списка товаров;
- проверка API Key через HTTP-заголовок `X-Api-Key`;
- аутентификация пользователя и генерация JWT-токена;
- проверка подписи и срока действия JWT;
- защита конечной точки с помощью `[Authorize]`;
- передача токена через заголовок `Authorization: Bearer`;
- обработка запросов с отсутствующим, изменённым и просроченным токеном.

Проверка приложения выполняется с помощью Swagger и HTTP-запросов.
